ҲУЖЖАТНИ ҚАНДАЙ ИШЛАТИШ КЕРАК

Ушбу файлни Claude'га тўлиқ беринг. Бу ишлаб чиқиш топшириғи; мавжуд код текширилгани ёки санаб ўтилган функциялар ҳозир тайёрлиги ҳақида ҳисобот эмас. Claude аввал мавжуд Online Magazin лойиҳасини текширади, кейин ушбу талабларни унга босқичма-босқич жорий қилади. Олдинги 35 бандли режа ва мавжуд код топилса, ҳар бири янги талабларга боғланади. Топилмаган файл, интеграция ёки тест натижаси бор деб кўрсатилмайди.

Мақсад — мижозга қулай харид, ҳамкорга шаффоф даромад, бизнесга бошқариладиган операциялар ва ишончли ҳисоб-китоб берадиган савдо платформасини қуриш. Ozon, Yandex Market, Wildberries ва Uzum функционал қамров учун мезон; уларнинг дизайни, коди, маълумоти ва бренди кўчирилмайди. Устунлик сотув конверсияси, етказиш сифати, ҳамкор даромадининг аниқлиги, қидирув, ўзбек тили, хизмат кўрсатиш ва операцион харажат орқали ўлчанади. Функциялар сонининг ўзи устунлик исботи эмас.

ҚАМРОВ

Ҳужжатда 64 та модуль, уларнинг роллари, ишлаш қоидалари, қабул сценарийлари, умумий маълумотлар модели, API ва ҳодиса шартномалари, молиявий инвариантлар, интеграция синовлари, босқичлар ва ишни топшириш мезонлари белгиланган. Ҳар бир модуль бутун тизим билан боғлиқ ҳолда бажарилади. Кейинги босқичга ажратиш талабни ўчириш дегани эмас; унинг эгаси, боғлиқлиги ва қабул шарти реестрда қолади.

АВВАЛГИ КЕЛИШУВЛАР ВА БОШЛАНҒИЧ ҚАРОРЛАР

1. Дастлабки бизнес модели: маҳсулотларни лойиҳа эгаси ва ваколатли ходимлари жойлайди; ҳамкорлар реклама қилиб сотув келтиради ва комиссия олади. Ҳамкор автоматик равишда маҳсулот эгаси ёки мустақил сотувчи бўлмайди.
2. Янги мақсадли архитектура ташқи сотувчиларни ҳам қўллайди. Биринчи сотувчи — лойиҳа эгасининг ташкилоти. Ташқи сотувчиларни қабул қилиш алоҳида бизнес режими орқали ёқилади. Бунинг учун буюртма, қолдиқ ва молияни кейин қайта қуриш талаб этилмасин.
3. Ҳамкор учун «Сайт Бирлиги» (Sayt Birligi) — SB номи сақланади. 100 000 сўмлик сотувдан 30 000 сўм комиссия, ҳар маҳсулот учун 1 SB, SB учун 4–5 минг сўмлик иқтисодий мўлжал ва 1000 SB эвазига iPhone 17 Pro — бизнес мисоллари. Улар тасдиқланган умумий тариф ёки кафолатланган айирбошлаш курси эмас. Амалдаги қийматлар версияланган қоидаларда белгиланади.
4. Online Magazin TAQVIM'дан мустақил: алоҳида репозиторий ёки алоҳида аниқ чегараланган лойиҳа, база, хизмат аккаунтлари, Docker конфигурацияси, домен ва релиз жараёни. TAQVIM ресурсларидан рухсатсиз фойдаланилмайди.
5. Мавжуд стек текширилмасдан алмаштирилмайди. Ишлайдиган кодни сақлаш ва аниқланган нуқсонларни тузатиш биринчи йўл. Зарур архитектура ўзгариши далил, миграция ва орқага қайтиш режаси билан асосланади.
6. Мижоз интерфейси учун ўзбек лотин, ўзбек кирилл ва рус тили мақсадли қамров; интерфейс, контент ва юридик ҳужжат тили алоҳида сақланади. Асосий валюта UZS, бизнес вақти Asia/Tashkent, базада вақт UTC.
7. Дастурни ёзиш, локал ва тест муҳитида ишлатиш, тестлар ва ҳужжат тайёрлаш ушбу топшириқ доирасига киради. Ишлаб турган серверга жорий қилиш, ҳақиқий пул ўтказиш, оммавий реклама юбориш ва ҳақиқий мижоз маълумотини ташқи AI'га бериш учун тегишли амалий рухсат ва шартномалар бўлиши керак. Бу талаблар код ва тестларни тайёрлашни тўхтатмайди.

CLAUDE УЧУН ИШЛАШ ТАРТИБИ

• Аввал файллар, стек, миграциялар, муҳит, тестлар, роллар ва интеграцияларни ўқи. Реал ҳолатни «ишлайди», «қисман», «йўқ», «блокланган», «текширилмаган» деб ажрат. Ҳар бир хулосага файл ёки тест далили қўш.
• Ҳар модул учун экранлар, сценарийлар, бизнес қоидалари, маълумотлар, endpoint'лар, event'лар, рухсатлар, истиснолар, тест ва кузатув метрикаларини ишлаб чиқ. Ушбу ҳужжатдаги ID'лар код вазифалари ва қабул далилларида сақлансин.
• Бир вақтда бутун платформани аралаш ўзгартириш ўрнига, ишлайдиган тўлиқ жараёнларни кетма-кет якунла: интерфейс → API → база → бизнес қоидаси → интеграция → тест → кузатув.
• Тугма борлиги функция тайёрлигини англатмайди. Тугма ҳақиқий амал бажарсин; юкланиш, бўш натижа, хатолик, рухсат йўқлиги ва қайта уриниш ҳолатлари ҳам бўлсин. Тест маълумоти ҳақиқий натижа сифатида кўрсатилмасин.
• API калити ёки ташқи шартнома берилмаган бўлса, адаптер, sandbox сценарийлари ва контракт тестларини тайёрла. Ҳисоботда айнан қайси ташқи қадам етишмаётганини кўрсат. Имитация қилинган тўловни «интеграция тугал» деб белгилама.
• Қоидага таъсир қилувчи янги тахминни decision log'га ёз. Маълум талабни қайта сўраб ишни тўхтатма. Нарх, солиқ, шартнома ва маблағ етарлилиги каби очиқ бизнес қарорларини релиздан олдинги аниқ рўйхатга йиғ.
• Ҳар босқич охирида ўзгариш, текширув натижаси, ишламайдиган қисм ва кейинги боғлиқликни қисқа ҳисобот қил. Тестларнинг ўтган, йиқилган ва skip сонини реал логдан ол; уларни тахмин қилма.

АТАМАЛАР ВА РОЛЛАР

Мижоз — харид қиладиган шахс; меҳмон ҳолатида ҳам каталог ва рухсат этилган checkout'дан фойдаланади.
Ҳамкор — affiliate; тасдиқланган канал ёки ҳавола билан сотув келтиради, комиссия ва SB ишлайди.
Сотувчи — merchant; юридик ёки шартномавий савдо иштирокчиси, таклиф, қолдиқ, буюртма ва ҳисоб-китобга эга.
Таъминотчи — supplier; омборга товар етказиб беради. У мижоз олдидаги сотувчи бўлиши шарт эмас.
Оператор — буюртма ва лидларни белгиланган ваколатда қайта ишлайди.
Қўллаб-қувватлаш — мурожаат, қайтариш ва низони кўради; молиявий ҳуқуқи алоҳида берилади.
Контент менежери — каталог, медиа, таржима ва саҳифаларни тайёрлайди.
Омбор ходими — қабул, жойлаш, йиғиш, санаш ва жўнатишни бажаради.
Курьер ва қабул пункти ходими — фақат бириктирилган жўнатма ва топшириш маълумотини кўради.
Молия ходими — солиштириш, ҳисобот, refund ва payout'ни ваколатига қараб тайёрлайди.
Модератор ва риск мутахассиси — маҳсулот, шарҳ, контент ва шубҳали операцияларни текширади.
Админ — белгиланган модулларни бошқаради. Superadmin — сиёсат ва ҳуқуқларни бошқаради; молиявий тарихни ўчириш ваколатига эга эмас.
Аудитор — ўқиш ҳуқуқи билан далил ва ҳисоботни текширади.
AI хизмат аккаунти — инсоннинг амалдаги ҳуқуқидан ортиқ ваколат олмайди; алоҳида хизмат идентификатори ва чекланган tool'ларга эга.

Бир инсон бир нечта ролга эга бўлиши мумкин. Рол алмашиши экран ва ресурс контекстини аниқ ўзгартиради; мижоз бўлиб кирган ҳамкор бошқа мижоз буюртмасига кира олмайди. Рухсат API ва маълумотга кириш қатламида текширилади.

МОДУЛЛАР УЧУН УМУМИЙ ҚАБУЛ ШАРТИ

Ҳар модулда қуйидаги ҳолатлар текширилади: оддий жараён, рухсатсиз мурожаат, маълумот йўқлиги, нотўғри киритиш, ташқи хизмат ишламаслиги, такрорий сўров, параллел ўзгариш ва мобил экран. AC-Mxx-1 ва AC-Mxx-2 — модулнинг мажбурий қабул сценарийлари; булар барча тестларнинг ўрнини босмайди. Тўлиқ traceability матрицасида ҳар бир қоида камида битта автоматик ёки асосланган қўлдаги текширувга боғланади.

I МИЖОЗ ВА САВДО ЖАРАЁНИ

M01 Бизнес конфигурацияси ва савдо режимлари

Эгалар: бизнес эгаси, админ, молия. Ташкилот, бренд, домен, валюта, вақт минтақаси, хизмат ҳудуди, алоқа, сотув модели, оферта ва feature flag'лар марказдан бошқарилсин. owner_only ва multi_merchant режимлари бир хил савдо ядросида ишласин. Юридик сотувчи, товар эгаси, тўловни олувчи ва фискал чекни берувчи алоҳида белгилансин. Конфигурация версияси, кучга кириш вақти, ўзгартирган шахс ва таъсир доираси сақлансин. Комиссия ёки қайтариш қоидасини ўзгартириш аввалги буюртма шартларини яширинча ўзгартирмасин. Савдо канали ва регион бўйича хизматни вақтинча чеклаш сабаби мижозга тушунарли кўринсин.
AC-M01-1: owner_only режимида affiliate API орқали ҳам маҳсулот ярата олмайди; эганинг ваколатли ходими ярата олади.
AC-M01-2: янги тариф ёқилганда эски буюртманинг нарх ва шартнома snapshot'и ўзгармайди; янги буюртма янги версияни олади.

M02 Кириш ва аккаунтни бошқариш

Телефонни E.164 форматда нормаллаштириш, OTP, муддат, қайта юбориш интервали, уриниш лимити, session'лар рўйхати ва чиқиш ишласин. +998 ва маҳаллий ёзувлар бир рақамга келтирилсин. Guest checkout қўллансин; аккаунт яратиш саватни йўқотмасин. Телефонни алмаштиришда эски ва янги эгаликни текшириш ёки назоратли recovery бўлсин. Бир хил рақамни киритишнинг ўзи бошқа аккаунтни бирлаштиришга асос эмас. Telegram ёки бошқа social login алоҳида тасдиқланган боғлаш орқали ишласин. Админ, молия ва сотувчи эгаларига қўшимча тасдиқ; recovery'да ҳам ўша ҳимоя сақлансин. Аккаунтни ёпиш, блокдан шикоят ва тарихий ҳужжатларни сақлаш қоидалари ажратилсин.
AC-M02-1: OTP қайта ишлатилмайди; аккаунтга кирилганда меҳмон савати аниқ қоида бўйича бирлашади ва дубль товар сони нотўғри ошмайди.
AC-M02-2: рақам ўзгарганидан кейин бошқа инсон эски рақам орқали аввалги буюртмаларни ололмайди; recovery амали аудитда қолади.

M03 Шахсий кабинет ва манзиллар

Профиль, манзиллар, қабул қилувчи, буюртмалар, қайтаришлар, чеклар, кафолат, сақланган товарлар, обуналар, мурожаатлар ва махфийлик созламалари бўлсин. Манзил: вилоят, туман/шаҳар, маҳалла, кўча, уй, хонадон, қават, ориентир, координата ва етказиш изоҳи. Харита ва қўлда киритиш тенг ҳуқуқли йўллар бўлсин. Текширилган етказиш ҳудуди ва тариф манзилга боғлансин. Буюртмада манзил snapshot'и сақланиб, профиль манзили ўзгариши жўнатилган буюртмани ўзгартирмасин. Бошқа қабул қилувчи маълумоти фақат шу етказиш учун ишлатилсин. Карталарнинг фақат провайдер токени ва маскаланган кўриниши сақлансин.
AC-M03-1: GPS рад этилганда мижоз манзилни қўлда киритиб буюртма бера олади.
AC-M03-2: сақланган манзил ўчирилса ҳам аввалги буюртманинг ҳужжати сақланади; бошқа аккаунт уни кўрмайди.

M04 Тиллар ва барча учун қулай интерфейс

Лотин, кирилл ва рус тили учун i18n калитлар, кўплик, сана, сумма, хатолар, SMS/push ва админ экранлари қамралсин. Танлов аккаунтда ва меҳмон қурилмасида сақлансин; браузер тили кейинчалик уни босиб кетмасин. Товар номи, таржима, оригинал бренд ва техник модель аралаштирилмасин. 360–1440 px оралиқда responsive дизайн, light/dark, клавиатура, screen reader, кўринадиган focus, катта матн ва камайтирилган анимация режими бўлсин. WCAG 2.2 AA мақсад қилиб белгилансин [S10]. Ранг ягона статус белгиси бўлмасин. Нарх, хатолик ва тўлов натижаси овозли ўқишда тушунарли бўлсин.
Оддий саҳифалар 320 CSS px кенгликда ҳам икки томонлама scrollсиз қайта жойлашсин; ҳақиқатан икки ўлчамли жадвал/харита учун асосланган истисно ва қулай кўриш усули. Бу 200 фоиз матн катталаштиришдан алоҳида reflow текшируви. Барча ички панеллар ҳам қамралсин. OTP paste/autofill ва password manager тўсилмасин.
AC-M04-1: тил алмашиши сават, фильтр ва checkout маълумотини сақлайди; untranslated key экранда чиқмайди.
AC-M04-2: товар танлашдан буюртмани тасдиқлашгача клавиатура ва screen reader билан ўтиш мумкин; 200 фоиз катта матн тугмаларни беркитмайди.

M05 Бош саҳифа ва контент бошқаруви

Бош саҳифа, тематик лендинг, акция, бренд ва ҳамкор жалб қилиш саҳифалари блоклардан бошқарилсин. Баннер, коллекция, видео, ишончли сервис маълумоти, категория ва тавсия блоклари учун draft, preview, тасдиқ, schedule, publish ва rollback бўлсин. Контент ҳудуд, тил, қурилма ва мавсумга мос кўрсатилсин; шахсийлаштиришга розилик инобатга олинсин. Блокдаги нарх ва қолдиқ савдо API'сидан келсин; контент ичида қолиб кетган эски нарх билан сотилмасин. Сунъий «ҳозир 500 киши кўрмоқда» ва сохта таймер қўлланмасин. Келажакдаги акцияни оддий preview URL оммага очиб бермасин.
AC-M05-1: белгиланган вақтда акция ёқилади ва тугайди; кэшда тугаган нарх checkout'га ўтмайди.
AC-M05-2: нотўғри блок версияси қайтарилганда аввалги саҳифа тикланади, маҳсулот ва буюртмаларга таъсир қилмайди.

M06 Категориялар ва брендлар

Иерархик категория, бренд, коллекция, категорияга хос атрибут, ўлчов бирлиги, вариант, фильтр ва сертификат талаби бўлсин. Дарахтда цикл, такрор slug ва тегишсиз атрибутни чекла. Категорияни кўчириш URL, breadcrumb, қидирув индекси, товар mapping ва redirect режаси билан бажарилсин. Категорияда қайтариш сиёсати, комиссия, етказиш чеклови ва модерация талаби бўлиши мумкин; уларнинг манбаси ва устуворлиги аниқ бўлсин. Бренд ҳуқуқи бўйича ҳужжат ва даъво жараёни сақлансин. Бир товарнинг турли сотувчи таклифлари бир каноник карточкага боғланиши мумкин.
AC-M06-1: категория кўчирилганда товарлар йўқолмайди; эски URL тегишли янги манзилга ўтади.
AC-M06-2: смартфонга кийим ўлчами каби номос атрибут берилмайди; мажбурий атрибутсиз товар publish бўлмайди.

M07 Қидирув ва маҳсулотни топиш

Ном, бренд, SKU, штрихкод, хусусият ва синоним бўйича қидирув; ўзбек лотин/кирилл нормаллашуви, апостроф вариантлари, рус тили, имло хатоси ва транслитерация қўллансин. Аниқ модель ва рақамлар йўқолмасин: 128 GB билан 256 GB тенглаштирилмайди. Autocomplete, категория таклифи, нарх, қолдиқ, сотувчи, рейтинг, етказиш ва атрибут фильтрлари URL'да сақлансин. Сортлаш, zero-result ёрдами, оммабоп ва яқин вариантлар бўлсин. Реклама натижаси белгилансин. Search индекси нарх/қолдиқнинг якуний манбаси эмас; checkout ҳақиқий маълумотни текширади. Қидирув сифати эталон ўзбекча сўровлар тўплами билан ўлчанади.
AC-M07-1: «қулоқчин», «quloqchin» ва тегишли русча синонимлар кутилган каталогни топади; серия рақами ўзгармайди.
AC-M07-2: қидирув хизмати ишламаса категория навигацияси ва аниқ SKU орқали харид сақланади; хато тушунарли чиқади.

M08 Маҳсулот саҳифаси ва таққослаш

Галерея, видео, вариантлар, ҳақиқий сотувчи, нарх/чегирма, мавжудлик, манзилга етказиш баҳоси, хусусият, комплект, ўлчам жадвали, қўлланма, кафолат, қайтариш шарти, сертификат ва савол-жавоб кўрсатилсин. Вариант алмашганда расм, нарх, SKU ва қолдиқ биргаликда ўзгарсин. Бўлиб тўлашда жами тўлов ва шартлар провайдер маълумоти билан берилсин. Таққослаш бир категориядаги мос атрибутларга асослансин; номаълум маълумот «йўқ» деб сохталаштирилмасин. Алтернатив сотувчи таклифида етказиш ва қайтариш шартлари очиқ бўлсин. Маҳсулот архивланса, тарихий буюртма карточкаси сақлансин.
AC-M08-1: ранг/хотира варианти алмашганда саватга айнан танланган SKU қўшилади.
AC-M08-2: нотўғри ёки йўқ хусусият AI орқали тўлдирилган факт сифатида кўрсатилмайди; модерацияга вазифа очилади.

M09 Сараланганлар ва шахсий кузатувлар

Wishlist, маҳсулот тўпламлари, нарх пасайиши ва қолдиқ пайдо бўлиши ҳақида обуна, қайта кўрилган товарлар, харидни давом эттириш бўлсин. Меҳмон рўйхати аккаунтга кирганда бирлашсин. Обуна SKU, ҳудуд, сотувчи ва нарх чегарасига боғлансин. Хабар юборишдан аввал шарт қайта текширилсин, бир ўзгариш учун такрорий хабарлар чеклансин. Мижоз кузатув тарихини тозалай олсин. Shared wishlist очиқ ёки ёпиқ экани аниқ, киришни бекор қилиш мумкин бўлсин; манзил ва телефон унга кирмасин.
AC-M09-1: бошқа ранг омборга келганда танланган рангга обуна бўлган мижозга асоссиз хабар кетмайди.
AC-M09-2: обуна бекор қилинганда навбатдаги маркетинг хабарлари ҳам тўхтайди; муҳим буюртма хабари бунга боғланмайди.

M10 Шарҳлар ва савол жавоб

Тасдиқланган харид белгиси, рейтинг, матн, фото/видео, фойдали деб баҳолаш, шикоят, сотувчи жавоби ва модерация бўлсин. Харид тасдиғи ҳақиқий берилган товар билан боғлансин. Модерация қоидаси, рад сабаби ва апелляция мавжуд бўлсин; салбий фикрнинг ўзи ўчириш сабаби эмас. Шарҳ учун бонус бўлса, очиқ кўрсатилсин ва ижобий баҳо бериш шарти қўйилмасин. Ботлар, дубль ва ҳақоратга қарши назорат бўлсин. Саволга AI жавоби алоҳида белгиланиб, каталог далилига боғлансин. Шахсий маълумот оммага чиқмасин.
Маҳсулот сифати рейтинги, сотувчи хизмати ва етказиш баҳоси алоҳида. Бир сотувчининг кечикиши бошқа сотувчининг service score'сига ёки маҳсулотнинг техник хусусияти баҳосига автоматик аралашмасин.
AC-M10-1: маҳсулот сотмаган affiliate ўзини тасдиқланган харидор қилиб кўрсата олмайди.
AC-M10-2: рад этилган шарҳ бўйича сабаб ва апелляция тарихи сақланади; рейтинг қайта ҳисобланганда дубль ҳисобланмайди.

M11 Сават ва буюртмани расмийлаштириш

Сават variant/offer даражасида: сони, мавжудлиги, совға, купон, етказиш ва сотувчи гуруҳлари. Guest ва аккаунт саватини бирлаштириш қоидаси аниқ бўлсин. Checkout: манзил → етказиш варианти → тўлов усулини танлаш → тўлиқ ҳисоб → шартларни қабул қилиш → буюртмани тасдиқлаш. Ҳақиқий payment attempt тасдиқланган quote/order ва зарур резервдан кейин бошланади. Минимал майдонлар, тушунарли хатолар, қайта юкланишдан тиклаш бўлсин. Сервер quote яратсин: нарх, чегирма, солиқ, етказиш, мижоз тўлайдиган жами сумма ва амал қилиш муддати. Quote эскирса янги ҳисоб мижозга кўрсатилсин. Ихтиёрий товар алмаштиришга олдиндан розилик бўлмасдан йўл қўйилмасин. Double-click ва тармоқ retry битта буюртмага олиб келсин.
AC-M11-1: checkout пайтида нарх ўзгарса, мижоз янги жами суммани тасдиқламасдан тўлов бошланмайди.
AC-M11-2: бир хил idempotency key билан уч марта юборилган тасдиқ битта order ва битта stock reservation яратади.

M12 Нарх ва акциялар механизми

Базавий нарх, регион/канал нархи, B2B нарх, markdown, купон, bundle, миқдор чегирмаси, бепул етказиш ва кампания бюджети қўллансин. Қоидалар устуворлиги, биргаликда қўлланиши, eligibility, лимит, бошланиш/тугаш, round ва funding_owner сақлансин. Нархни client юборган суммага ишониб ҳисоблама. Сават чегирмаси сатрларга детерминистик тақсимлансин; охирги тийин фарқи аниқ қоида билан берилсин. Қайтаришда айнан шу тақсимот ишлатилсин. Сотувчи, платформа ва бренд тўлайдиган скидкалар ажратилсин. Катта нарх хатоси учун карантин ва тасдиқ; сохта «эски нарх» тақиқлансин.
AC-M12-1: акция бюджетига бир вақтда келган буюртмалар лимитдан ортиқ бонус олмайди.
AC-M12-2: 3 сатрга тақсимланган чегирманинг йиғиндиси умумий скидкага тенг; қисман refund аввалги тақсимотни сақлайди.

M13 Буюртмаларни бошқариш

Customer order, merchant order, order line, shipment ва payment алоҳида объектлар бўлсин. Ҳар бир сатрда сотувчи, SKU, миқдор, нарх, солиқ, скидка, affiliate attribution ва қоида версиялари snapshot қилинади. Буюртманинг савдо ҳолати, тўлов ҳолати, етказиш ҳолати ва refund ҳолати битта status'га тиқилмайди. Қисман бекор қилиш, қисман жўнатиш, қисман бериш ва қайта етказиш қўллансин. Оператор ўзгартишлари версия назорати, сабаб ва ҳуқуқ билан бажарилсин. Мижозга оддий бирлаштирилган статус ва ҳар жўнатма тафсилоти кўрсатилсин. Қайта буюртма янги нарх ва қолдиқни текширсин. Тўланган буюртмани маълумотни ўчириш орқали бекор қилиш мумкин эмас.
AC-M13-1: икки сотувчи буюртмасининг бири бекор бўлса, иккинчисининг тўлов/жўнатмаси йўқолмайди.
AC-M13-2: бир операторнинг эски экрандан сақлаши иккинчисининг янги ўзгаришини босиб кетмайди; conflict кўрсатилади.

M14 Тўловлар ва провайдер адаптерлари

Payme, Click ва шартнома бўлса бошқа маҳаллий банк/бўлиб тўлаш провайдерлари ягона ички интерфейсга улансин. Ҳар провайдернинг capability матрицаси: тўлов, текшириш, бекор қилиш, тўлиқ/қисман refund, split ва фискал маълумот. Қўлланмайдиган амал бор деб кўрсатилмасин. Payment intent ва ҳар уриниш алоҳида; timeout — номаълум натижа, автоматик «тўланмади» эмас. Webhook аутентификацияси, сумма, валюта, account/order mapping, дубль ва кечиккан хабар текширилсин. Redirect тўлов исботи эмас. Payme amount тийинда белгиланган [S05]; ички Money ҳам integer minor-unit бўлсин. Click Prepare/Complete жараёни расмий шартнома бўйича мослансин [S06]. COD ва банк ўтказмаси алоҳида settlement жараёнига эга бўлсин.
Chargeback/банк низоси алоҳида case: provider case ID, асл transaction, сумма/валюта, жавоб муддати, далил, provisional debit, won/lost/reversed, reserve ва reconciliation. Оддий support ticket уни алмаштирмайди. Refund билан тўқнашув 9.5 ва 9.7 қоидаларида ҳал қилинади.
AC-M14-1: бир хил provider transaction хабарининг 20 та такрори битта молиявий натижа яратади.
AC-M14-2: икки тўлов канали бир буюртма учун пул олса, иккинчи сумма аниқланади ва excess-payment/refund жараёнига тушади; иккинчи товар жўнатилмайди.

M15 Чеклар ва юридик ҳужжатлар

Буюртма тасдиғи, оферта версияси, фискал чек, қайтариш чеки, ҳисоб-фактура, далолатнома ва сотувчи реквизитлари тегишли модель бўйича юритилсин. Фискал адаптерда товар таснифи, бирлик, солиқ атрибути, сотувчи, сумма, скидка ва тўлов маълумоти расмий провайдер контрактига мос бўлсин. Ҳужжат яратиш, юбориш, рад этилиш, қайта уриниш ва тузатиш ҳолатлари алоҳида сақлансин. Провайдер timeout берганда чек иккинчи марта яратилиб кетмасин. Order'ни «paid» деб белгилаш фискал чек муваффақияти билан аралаштирилмасин; ҳуқуқий талабга кўра кейинги амаллар чекланиши мумкин. Мижоз ҳужжатни юклаб олади; ҳуқуқи йўқ шахс PDF URL орқали ололмайди.
AC-M15-1: чек хизмати ўчганда тўлов йўқолмайди; pending fiscal вазифаси пайдо бўлади ва тиклангач дубльсиз бажарилади.
AC-M15-2: қисман қайтариш тегишли сатр ва суммага мос тузатиш ҳужжатини яратади; тарихий чек ўчирилмайди.

M16 Бекор қилиш қайтариш ва кафолат

Мижоз сатр ва миқдорни танлаб RMA очади: сабаб, фото, текшириш, қайтариш усули, муддат, қарор, апелляция ва пул ҳолати кўринади. Бекор қилиш, қабул қилмаслик, сифатли товарни алмаштириш, нуқсонли товар, кафолат таъмири ва recall алоҳида сценарийлар. Сиёсат категория, сабаб, етказилган сана, ҳолат ва амалдаги ҳуқуққа боғлансин; ҳамма товарга битта «10/14/30 кун» қоидаси hardcode қилинмасин [S09]. Refund товар, етказиш ва бошқа тўловлар бўйича ажратилсин. Returned, inspected, refund_pending ва refunded турли ҳолатлар. Алмаштиришда эски қайтариш ва янги жўнатма боғланади; нарх фарқи аниқ ҳисобланади. Кафолат ҳуқуқи affiliate hold тугагани учун йўқолмайди.
AC-M16-1: бир сатрдан 2 та олиниб 1 таси қайтарилса, refund/қолдиқ/комиссия айнан 1 тага ўзгаради.
AC-M16-2: провайдер refund'ни қабул қилиб жавоби йўқолса, retry ортиқча пул қайтармайди; мижозда «қайтарилмоқда» ҳолати қолади.

M17 Хабарномалар ва алоқа каналлари

In-app, SMS, email, web/mobile push, Telegram ва шартнома/рухсатга эга бошқа каналлар адаптер орқали ишласин. Transactional ва marketing хабарлари алоҳида. Тил, quiet hours, розилик, канал устуворлиги, муҳимлик, дедупликация, provider receipt, retry ва dead-letter queue сақлансин. OTP билан реклама навбати ажратилсин. Telegram аккаунтини боғлаш тасдиқлансин; Instagram/WhatsApp имконияти расмий API ҳуқуқи ва амалий чекловга қараб ёқилсин. Мижоз матнида шахсий маълумот керагидан ортиқ чиқмасин. Бир event бир нечта каналга атайин юборилса, мақсад ва лимит аниқ бўлсин. Бир кампанияни икки scheduler ишга туширса, икки марта юборилмасин.
Шахсий кабинетда канал/мақсад бўйича preference center, quiet hours ва розилик тарихи бўлсин. Юбориш пайтида consent билан бирга жорий order/stock ҳолати қайта текширилади; тўланган буюртма учун эски «тўланг» хабари кетмайди. OTP ва зарур хавфсизлик хабарлари учун quiet hours сиёсати алоҳида.
AC-M17-1: marketing'дан чиқиш реклама SMS'ни тўхтатади, хавфсизлик ва буюртмага зарур хабарлар сиёсати алоҳида ишлайди.
AC-M17-2: SMS провайдери ишламаса келишилган fallback ишлайди; юборилмаган хабар «етказилди» деб ҳисобланмайди.

M18 Мижоз бонуслари сертификатлар ва обуналар

Мижоз loyalty дастури affiliate SB'дан алоҳида program_id ва ledger билан юритилсин. Бонус earning, pending, available, expiry, redemption ва reversal қоидалари кўрсатилсин. Совға сертификатида issuer, баланс, валюта, муддат, қўллаш ва refund сиёсати; сотиб олинган қиймат билан promotional бонус ажратилсин. Сертификат чиқариш ва ишлатиш молиявий мажбурият сифатида назорат қилинади. Аъзолик/обунада имтиёз, янгиланиш, бекор қилиш, шартлар ва провайдер recurring capability'си текширилсин. Автоматик тўлов фақат аниқ розилик ва мос PSP механизми билан. Реал пул ечиладиган универсал e-wallet ушбу бонус балансидан автоматик келиб чиқмайди.
Refund'да purchased value ва promotional credit ўз табиатини сақлайди; promo бонус нақд қайтимга айланмайди. Тикланган бонуснинг expiry/eligibility қоидаси версияли. Обуна учун upcoming renewal, pause/skip, cancellation effective date, retry ва янги нархга розилик; ҳар цикл алоҳида order/invoice/payment reference'га эга. Битта цикл икки марта тўланмайди.
AC-M18-1: бир сертификатни икки checkout бир вақтда ишлатса, умумий сарф унинг қолдиғидан ошмайди.
AC-M18-2: affiliate SB билан мижоз бонуси аралашмайди; қайтаришда нақд/сертификат/бонус улушлари олдинги тўловга мос тикланади.

II КАТАЛОГ ОМБОР ВА ЕТКАЗИБ БЕРИШ

M19 Маҳсулот маълумотларини бошқариш

Product — каноник маҳсулот; variant/SKU — сотиладиган аниқ вариант; offer — сотувчининг нарх ва шартлари; stock — омбордаги миқдор. Булар алоҳида моделлансин. Ном, тавсиф, атрибут, бренд, штрихкод, оғирлик, габарит, комплект, модел, кафолат, серия/партия талаби, солиқ таснифи ва category policy сақлансин. Каталог нархи ўзгарганда аввалги тасдиқланган redemption сақланади. Redemption quote → SB ва совринни биргаликда резерв → тасдиқ → йиғиш/харид → етказиш → ёпиш. Бекор қилиш, муддат ўтиши, йўқолиш, нуқсон ва replacement жараёни. Совринни бошқасига розиликсиз алмаштирма. Fraud review чексиз ҳолат эмас: масъул ва муддат бўлсин. Муваффақиятсиз етказишда балл ва соврин ҳолати мувофиқ қайтарилсин. Телефоннинг бозор нархи ушбу ҳужжатда тахмин қилинмайди.
Омбордаги соврин учун physical reserve; кейин харид қилинадиган соврин учун тасдиқланган procurement quota, маблағ резерви ва аниқ етказиш ваъдаси. Қайтган соврин inspection'дан кейингина sellable'га ўтади. Бюджет cap янги мажбуриятни чеклайди, аввал qualified бўлган SB/совринни бекор қилмайди.
AC-M33-1: охирги 1 совринга икки ҳамкор сўров берганда фақат бири stock+SB резервини олади.
AC-M33-2: redemption бекор қилинса резервдаги SB айнан бир марта тикланади ва соврин омбори ҳолати ҳам мос келади.

M34 Мусобақалар ва ҳамкор ривожи

Кеч event, refund ва appeal учун cutoff ва тузатиш протоколи. Public nickname розилик билан; шахсий даромадни очиш ихтиёрий. Малака курслари, материаллар, completion ва сертификатлар reward eligibility'сига аниқ боғланиши мумкин. Пул тўлаб тасодифий соврин ютиш ёки янги ҳамкор жалб қилгани учун чекланмаган занжирли тўлов киритилмасин.

AC-M34-1: охирги дақиқадаги сотув кейин қайтса provisional рейтинг тўғриланади; final натижа далилсиз таҳрирланмайди.
AC-M34-2: тенг натижада эълон қилинган tie-breaker бир хил ишлайди; бир ҳамкор бир совринни дубль ола олмайди.

M37 Таклифлар рақобати ва сотувчи сифати

Seller score: on-time shipment, cancellation, return reason, complaint, data quality; етарли маълумотсиз янги сотувчига ноҳақ рейтинг берилмасин. Тариф/санкция ва уларга апелляция. Товар асллиги, сертификат, тақиқланган категория ва ҳуқуқ эгаси даъвоси. Сотувчи offer'и бекор бўлса мижознинг буюртмаси бошқа сотувчига розиликсиз ўтказилмасин.

M38 Сотувчи ҳисоб китоби ва реклама кабинети

Settlement statement ҳар бир order line ва шартнома версиясигача очилсин. Тўлов графиги, minimum, hold, payout, reconciliation ва баҳс жараёни. Affiliate комиссияси кимнинг ҳисобидан тўланиши икки марта ушланмасин. Рекламада campaign, креатив moderation, бюджет, bid, billing model, attribution ва invalid traffic сиёсати. Тасдиқланган лимитдан ортиқ сарф бўлмасин; реклама натижаси кафолатланмасин. Реклама ҳисоботи савдо GMV'си билан revenue'ни аралаштирмасин. Ҳамкор ва merchant бир шахс бўлса ҳам икки ҳисоб алоҳида.

M42 Молиявий журнал ва солиштириш

Immutable double-entry ledger ёки мувозанати исботланадиган accounting subledger: cash/bank, PSP receivable, courier cash, customer advance/refund liability, merchant payable, affiliate payable, platform fee, promotion funding, reward obligation ва suspense. Даврни ёпиш, lock date, late adjustment ва версияланган экспорт. Ҳисоботдан ҳар бир сумма қайси операциядан келганига ўтиш мумкин бўлсин.

IX ҲИСОБ КИТОБ ФОРМУЛАЛАРИ ВА ИНВАРИАНТЛАР

9.1 Қолдиқ семантикаси

Танланган модель: on_hand_sellable — омбордаги яроқли, жўнатилмаган жисмоний миқдор; резервланган товар ҳам шу сон ичида. active_reservations — unpaid ва paid/allocated, аммо ҳали жўнатилмаган мантиқий ажратишлар. Quarantine/damaged/in_transit on_hand_sellable'га кирмайди. raw_ATP = on_hand_sellable − active_reservations − safety_buffer; мижозга бериладиган ATP = max(0, raw_ATP). Янги резерв qty ≤ ATP шарти билан атомар. Paid allocation active_reservations'га киргани учун иккинчи марта айирилмайди. Физик камомадда on_hand_sellable < active_reservations бўлса deficit яширилмайди: shortage case, таъсирланган order ва қайта allocation/refund жараёни. Dispatch физик чиқим ва резерв consume'ни бир транзакцияда бажаради. Unpaid expiry paid резервни чиқармайди. Cancellation/dispatch параллеллиги ва bundle компонентлари бир хил транзакцион қоидада ҳал қилинади.

9.2 Нарх ва тақсимот

Line gross = unit_price × ordered_quantity.
Line product net = line gross − line discount − allocated cart discount.
Order payable = Σ(line product net) + delivery + disclosed service fees − applicable payment credits. Солиқ нархга киритилган ёки қўшиладиган бўлса tax_policy'га кўра бир марта ҳисобланади; tax-inclusive нарх устига қайта солиқ қўшилмайди.
Сават скидкасини сатрларга тақсимлаш: eligible базага пропорционал exact share; minor-unit'га пастга яхлитлаш; қолган бирликларни энг катта fractional remainder бўйича, тенгликда stable line_id бўйича тарқатиш. Σallocated_discount = total_discount ва ҳар line net ≥ 0. Яхлитлаш сиёсати хизматлар/солиқ билан мувофиқлаштирилиб snapshot'да сақланади.

9.3 Комиссия мисоли

Фақат моделни текшириш учун: товарнинг чегирмадан кейинги, tax-inclusive нархи 100 000 сўм; етказиш 15 000 сўм; affiliate rate 30 фоиз. Commission basis=100 000, commission=30 000; етказиш базага кирмайди. 40 000 сўм товар қиймати қайтарилса cumulative reversed commission=12 000, қолган commission=18 000. 15 000 сўм фақат етказиш ҳақи қайтарилса, товар базаси ўзгармагани учун commission reversal=0. Булар тариф таклифи эмас, acceptance fixture.

Ҳар partial refund'да: янги cumulative_expected_commission = round(rule(original_snapshot, retained_eligible_basis)); adjustment = янги expected − аввалги нет ҳисобланган commission. Шу усул кўп кичик refund'да rounding хатоси йиғилишини чеклайди. Refund оригинал line allocation'дан ортиқ база қайтармайди. Fixed-per-unit комиссияда unit return ва price-only correction сиёсати алоҳида.

9.4 SB мисоли ва қийматни қайтариш

Демо қоида: eligible берилган ва пул тушган ҳар бир дона учун 1 SB; hold=H кун, H category/contract сиёсатида белгиланади. Икки донадан бири қайтса 1 SB сторно. Товар ўзи қолиб, нархнинг бир қисми компенсация қилинса, demo қоидада SB сақланади, лекин snapshot'даги minimum qualifying paid amount бузилса 1 SB ҳам сторно. Кафолат replacement бир янги qualifying sale эмас. Available cash/SB манфий қилиб яширилмайди; қарз алоҳида adjustment_debt бўлади. Кейинги earning'дан offset фақат қабул қилинган қоидага мувофиқ ва кўринадиган ҳаракат билан.

1 SB учун 4 500 сўм ички reward budget ажратилса, 1000 SB ортида 4 500 000 сўм режалаштирилган маблағ бўлади. Бу 1000 SB'га исталган телефонни бериш мумкин дегани эмас. Совриннинг actual procurement cost + delivery + тегишли харажатлари шу бюджетга мос бўлиши керак. Зарур SB threshold ≈ ceil(совриннинг жами харажати / бир SB учун ажратилган маблағ), ёки қўшимча sponsorship budget. Каталог қиймати ва молиявий provision сиёсати алоҳида тасдиқланади.

100 000 − 30 000 комиссия − 4 500 reward budget = 65 500 сўм. Бу фойда эмас: таннарх, PSP, етказиш субсидияси, солиқ таъсири, қайтариш ва операцион харажатлар ҳали айирилмаган. Масалан, таннарх 70 000 бўлса, қолган харажатларсиз ҳам −4 500 сўм. Шунинг учун комиссия/SB тартиби SKU contribution margin ва campaign cap билан симуляция қилинади. Қайтариш 5/15/30 фоиз, subsidy ва redemption rate сценарийлари бўйича stress test берилади; бу фоизлар бозор статистикаси эмас.

9.5 Пул ва refund чегаралари

Refundable amount = successful captured/collected allocation − completed refunds − pending refund reservations − аллақачон қайтарилган dispute/chargeback allocation. Ҳар ҳолатда provider'нинг settlement semantics'и билан солиштирилади. Refund ва chargeback бир вақтда бўлса бир customer entitlement икки марта қопланмасин. Қонуний қўшимча компенсация керак бўлса, у асл payment refund лимитини бузиш эмас, алоҳида approved expense/payment.

Бир account/currency учун cumulative raw_payout_position = matured entitlement − reversals − independent contractual offsets − active payout reservations − already paid. Ечиш мумкин бўлган available = max(0, raw_payout_position). Манфий позиция 9.7 бўйича тасдиқланган debt ёки submitted/unknown payout exposure'си сифатида алоҳида кўрсатилади; debt reversal'нинг projection'и бўлса иккинчи марта айирилмайди. Paid'га ўтишда ўша резерв биргаликда ёпилади. Ҳар қийматнинг ledger манбаси аниқ. Pending earning available'га қўшилмайди. PSP accepted билан bank settled фарқлансин. COD delivered, cash_collected ва cash_remitted алоҳида. Unknown натижа аниқланмагунча кўр-кўрона қайта payout йўқ.

Payable ноль бўлган қонуний gift/promotion/fully-covered certificate буюртмаси учун PSP'га 0 суммада сохта charge жўнатилмайди. Қоплаш манбалари ва order confirmation қоидаси сақланади; actual cash capture бўлмагани аниқ кўрсатилади. Ташқи провайдер minimum/maximum ва minor-unit чегаралари validation'да текширилади.

9.7 Бир вақтдаги ва натижаси номаълум операциялар

Ташқи провайдер idempotency key, reference бўйича status query, refund query ва cancel'ни қай даражада қўллаши capability матрицасида белгилансин. Чақирув бажарилиб жавоб йўқолса аввал ўша reference текширилади. Хавфсиз автоматик текшириш йўқ бўлса manual reconciliation; янги reference билан кўр-кўрона қайта юбориш йўқ. Ички dedupнинг ўзи банк ёки ташувчида duplicate'ни кафолатли тўхтатмайди. Бу M14/M24/M31/M53 қабул шартларининг бир қисми.

Refund × payout матрицаси: payout ҳали send қилинмаган reserved ҳолатда — тегишли резервни қайта ҳисоблаш/қисқартириш; submitted/unknown — натижа аниқлангунча пул қайта сарфланмасин; confirmed paid — шартномавий debt/offset. Бир refund ҳам резервни камайтириб, ҳам ўша суммага иккинчи қарз яратмасин. Ташқи банк тузатиши ва ички қарз adjustment'и reference билан боғланади.

Refund × chargeback: provisional disputed amount ва ҳақиқатан мижозга қайтган amount алоҳида. Очиқ низо refund authorization'га hold/қўлда кўриб чиқиш таъсирини кўрсатади; қонуний муддатлар инобатга олинади. Ташқи chargeback автоматик равишда барибир иккинчи қайтим қилиб юборса, тизим уни яширмайди: overcompensation exception, PSP билан claim ва мувофиқ accounting. Дастур назорат қила олмайдиган ташқи воқеага «ҳеч қачон бўлмайди» кафолати берилмайди.

Бир CustomerOrder/PaymentIntent учун битта charge currency; display, settlement ва reporting валюталари алоҳида. Турли валюталар қолдиғи қўшилмайди. Ҳар валютада balanced journal ва FX clearing; асл capture валютасига боғланган refund. SB quantity'си бухгалтериядаги reward provision суммаси эмас; 4 500 сўмлик режавий cost автоматик cash liability эмас.

INV21 Кампания бюджети тугаши аввалги шартда qualified бўлган комиссия/SB/совринни бекор қилмайди; cap янги мажбуриятларни назорат қилади.
INV22 Қўшалоқ ташқи пул ҳаракати аниқланса ҳар иккала факт қайд этилади; дубликат хабар билан ҳақиқий иккинчи тўлов фарқланади.

INV23 Feature flag ёки provider shutdown янги сўровни чеклаши мумкин, аммо аввал бошланган order/payment/refund'ларнинг callback, reconciliation ва compensation'ини йўқотмайди. Режимни ортга қайтариш active transaction'ларнинг сиёсатини изсиз алмаштирмайди.

9.8 Аналитика учун асосий таърифлар

Бошланғич dictionary: ordered product GMV — яратилган мос order line'ларнинг скидкадан кейинги товар суммаси; paid product GMV — ҳақиқий тўловнинг товарга ажратилган қисми; delivered product GMV — берилган миқдорнинг асл net нархи; net delivered GMV — тегишли товар қайтимлари/компенсацияларидан кейинги сумма. Delivery fee алоҳида. Tax-inclusive/exclusive кўриниши номда белгилансин. Бир parent order'нинг merchant/subshipment бўлиниши order count'ни асоссиз кўпайтирмасин. AOV, conversion, repeat rate ва LTV'да denominator, вақт ойнаси ва cohort қоидаси dictionary'да version'лансин. GMV бухгалтерия revenue'сига тенг деб олинмайди.

XII ЎЛЧАНАДИГАН СИФАТ МАҚСАДЛАРИ

12.1 Юк профиллари

Қуйидаги рақамлар таклиф этилган acceptance baseline; мавжуд тизимнинг реал қуввати эмас. P0'да бизнес forecast, hardware ва бюджет билан келишилиб версияланади. Рақам ўзгартирилса сабаб ва янги чегара очиқ қайд этилади.

L1 Пилот: 10 000 SKU, 10 merchant модели, 2 омбор, 100 concurrent virtual session, секундига 30 catalog/search request ва 2 order confirmation; 5 дақиқа warmup, 30 дақиқа барқарор синов.
L2 Ўсиш: 100 000 SKU, 500 merchant модели, 20 омбор, 1000 concurrent session, секундига 300 read/search ва 20 order confirmation; 60 дақиқа барқарор синов. Реал provider квоталари бузилмайди: юкда contract-validated simulator, алоҳида sandbox integration.
L3 Чўққи ва тикланиш: келишилган базанинг 2 баравари 5 дақиқа; бир SKU flash sale; worker/DB/search узилиши; backpressure, queue drain ва reconciliation. Юкни рад этиш user-visible ва назоратли, тўловни номаълум ҳолатда қолдириш эмас.

Ҳисобот hardware/CPU/RAM/DB settings, data size, query mix, cache warm/cold, network, app commit, load generator, p50/p95/p99, throughput, unexpected errors, lock wait ва харажатни кўрсатади. «Миллион мижозни кўтаради» каби исботсиз хулоса берилмайди. TAQVIM сервери учун олдин айтилган ресурс marketplace sizing'и деб қабул қилинмайди.

12.2 Дастлабки хизмат мақсадлари

• Read API ички processing p95 ≤300 ms; p99 ≤1000 ms. Checkout quote/order commit p95 ≤800 ms; p99 ≤2000 ms, ташқи PSP жавоб вақти алоҳида ҳисобланади. Мижоз кўрадиган end-to-end вақт ҳам алоҳида берилади.
• Келишилган барқарор юкда unexpected server error rate <0.5%; expected validation, stock conflict ва rate-limit алоҳида саноқ. Critical молиявий/қолдиқ инвариант бузилиши — 0.
• Stock/price search index мақсадли кечикиши ≤60 s; ўзгарган active quote checkout'да ҳар доим authoritative сервер орқали текширилади. Кечикиш алертга эга.
• Асосий савдо учун ойлик availability мақсади 99.9%; ички ва dependency сабабли фойдаланувчига таъсир алоҳида ҳисобланади. Тест натижаси билан бир ойлик production SLO ўлчанди деб айтилмайди.
• Transactional база ва муҳим ҳужжатлар учун таклиф RPO ≤15 дақиқа, хизматни тиклаш RTO ≤2 соат; архитектура/бюджет тасдиғи ва restore drill шарт. Молиявий restore'дан кейин PSP/банк reconciliation мажбурий.
• Background queue учун вазифа турига кўра SLA: OTP алоҳида устувор навбат; муҳим payment/refund event'лар учун кечикиш чегараси; катта импорт/маркетинг асосий савдони босмасин. Provider rate limits ҳисобга олинсин.
• WCAG 2.2 AA қабул матрицаси; Web Vitals p75 мақсадлари M58'да. Реал мобил тармоқ ва ўрта тоифадаги қурилмада текширув бўлсин.

12.3 AI баҳолаш манифести

Дастлабки таклиф — 500 сценарий: 150 ўзбек лотин, 150 ўзбек кирилл, 150 рус, 50 аралаш ёзув. Shopping, product compatibility, order support, returns, policy version, escalation, content generation, price/stock freshness ва tool permissions қамралсин. Камида 20 фоиз tuning'да ишлатилмаган holdout. Катта model/prompt/tool ўзгаришида қайта eval; stochastic ҳолатларда бир нечта run ва variance.

Манифест: dataset version, source/ground truth, reviewer, model/prompt version, retrieval version, tool fixtures, test date, repetition, baseline, pass threshold, latency ва cost. Mock tool contract тестлари ҳақиқий model eval'дан ажратилсин.

Таклиф этилган сифат gate'лари: текшириладиган factual assertion'ларда ≥95% source-supported accuracy; келишилган вазифаларда ≥90% task completion; кўрсатилган нарх/қолдиқ current tool result'ига мос; escalation сценарийлари алоҳида precision/recall билан. Мижозга бегона маълумот бериш, тасдиқсиз муҳим амални бажариш ва бажарилмаган амални success деб билдириш critical suite'да 0. Бу чекланган test set учун қабул шарти, универсал нол риск кафолати эмас.

AI жавоби p95 мақсад ва бир task учун cost cap бизнес SLA'си билан ёзилсин; streaming орқали «тез кўринди» деб умумий кечикиш яширилмасин. Kill switch, provider fallback ва инсонга ўтиш қабул қилинмасдан AI default-on бўлмайди.

XIV ИШГА ТУШИРИШ ҚАРОРЛАРИ РЕЕСТРИ

Бу рўйхат ишни бошлаш учун ҳар сафар савол беришни талаб қилмайди. Claude хавфсиз test default'лар билан код, адаптер ва синовни тайёрлайди; ҳақиқий савдога таъсир қилувчи очиқ қийматлар live ёқилишидан олдин бизнес эгаси билан аниқланади. Демо қиймат production'га яширин кўчирилмасин.

D01 Бренд, домен ва дизайн identity: ишчи ном Online Magazin; аниқ бренд материаллари P0'да инвентаризация.
D02 Савдо модели: owner_only — аввалги келишув; multi_merchant — ушбу мақсадли спецификацияда тўлиқ қуриладиган режим.
D03 Юридик шахс, principal/agent модели, merchant-of-record, чек берувчи, солиқ сиёсати: аниқ ҳужжатга асосланади; Claude ихтиёрий танламайди.
D04 Affiliate ставкаси: percentage/fixed/tier ва funding_owner; 30 000/100 000 — тест мисоли, барча товар учун автоматик 30 фоиз эмас.
D05 Attribution: таклиф last eligible click 30 кун, explicit verified code устувор; consent ва self-referral сиёсати алоҳида тасдиқ.

D07 Payout minimum/maximum, график, fee, withholding, bank destination ва maker/checker threshold: версияланган қийматлар, ҳақиқий провайдер имконияти билан.
