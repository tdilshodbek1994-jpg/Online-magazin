## 01. АСОСИЙ БУЙРУҚ ВА ИШ ЧЕГАРАСИ

Сен мавжуд Online-magazin лойиҳасини давом эттираётган маҳсулот архитектори, full-stack муҳандиси ва тест муҳандисисан. Аввалги катта маркетплейс режасини архивлаштирилган келажак режаси сифатида сақла. Ҳозир унинг барча модулларини бирданига қурма.

Биринчи релизда магазин эгаси ўз маҳсулотларини жойлайди. Ваколатли ходимлар унга ёрдам беради. Ҳамкорлар маҳсулот эгаси эмас: улар шахсий ҳавола орқали харидор келтиради ёки харидорнинг розилиги билан унинг номидан буюртма киритади. Иккала усулдаги ҳақиқий сотувга бир хил қоидалар бўйича комиссия ҳисобланади.

Натижа — маҳсулотдан бошлаб буюртма, тўлов, омбор, етказиш, қайтариш ва ҳамкор билан ҳисоб-китобгача ишлайдиган тизим. Асосий мезон кўп экран эмас, савдо жараёнининг тўлиқ якунланиши.

Фақат Online-magazin репозиторийсида ишла. TAQVIM коди, сервери, базаси, токенлари, Docker тармоқлари ва контейнерларига тегма. Мавжуд ишларни ўчирма, нолдан қайта ёзма. Эгасининг алоҳида тасдиғисиз main’га merge, production deploy, сервер ёки тизим созламаларини ўзгартириш тақиқланади.

Ҳар модуль учун UI, backend, рухсатлар, маълумотлар модели, хатолик ҳолатлари, тест ва қабул далили талаб қилинади. TODO, чиройли макет ёки mock API натижасини тайёр функция деб топширма.

## 02. ТАСДИҚЛАНГАН ҚАРОРЛАР ВА СОЗЛАНАДИГАН СИЁСАТЛАР

Қатъий қабул қилинган бизнес қарорлари:

- Битта магазин эгаси ва битта савдо каталоги.
- Маҳсулот, базавий нарх, қолдиқ ва комиссия қоидасини эгаси ёки махсус ваколатли ходим бошқаради.
- Ҳамкорлар иккала усулда ишлайди: referral ҳавола ва мижоз номидан буюртма.
- Мижоз, ҳамкор, оператор ва бошқарув вазифалари ажратилган.
- Ҳамкорнинг шахсий кабинети, комиссия тарихи ва тўлов сўровлари бўлади.
- Мавжуд код сақланади; TAQVIM’дан тўлиқ ажратилади.

Ушбу ҳужжатдаги инженерлик таклифи: биринчи релиз UZS, Asia/Tashkent кўриниш вақти, ўзбекча кирилл ва лотин, битта асосий омбор билан ишласин. Базада вақт UTCда сақлансин. Катта multi-seller marketplace, мустақил сотувчи кабинетлари, кўп омборли маршрутлаш, SB, соврин ва конкурслар, натив мобил иловалар, кредит/бўлиб тўлаш ҳамда кўп даражали referral биринчи релизга кирмайди.

Комиссиянинг аниқ миқдори, referral амал қилиш муддати, комиссияни кутиш муддати, пул чиқариш минимал суммаси, етказиш тарифлари ва қайтариш шартлари эгаси тасдиқлайдиган версияланган сиёсатлардир. 100 000 сўмдан 30 000 сўм мисоли умумий 30% қоидаси эмас.

Тасдиқланмаган қийматни production default сифатида ёқма. Development/demo учун очиқ белгиланган fixture ишлат. Етишмаётган қарор код ёзишни тўхтатмасин: конфигурация, validation ва тестни тайёрла, live activation’ни тегишли қарорга боғла.

## 03. АВВАЛГИ ИШНИ САҚЛАШ ВА АУДИТ

Аввал repository remote, жорий branch, HEAD commit, иш дарахти ва мавжуд migration занжирини текшир. Аввалги бажарилган ишлар учун checkpoint branch/commit тайёрла; commitдан олдин махфий файлларни текшир. Рухсатсиз force push, reset --hard ёки файлларни оммавий ўчириш йўқ.

Аввалги 64 модулли режа репозиторийда бор бўлса, ўчирмасдан docs/future/ ичида сақла ёки унинг мавжуд йўлига ҳавола бер. Уни топмаган бўлсанг, ўқиганман деб ёзма. Ушбу ҳужжат Phase 1 scope бўйича устувор.

Иш feature/phase1-owner-affiliate каби алоҳида branchда бажарилсин. Ҳар ишлайдиган кичик босқич commit қилинсин. PR тавсифида ўзгаришлар, тестлар, migration ва қолган ташқи боғлиқликлар бўлсин.

## 04. РОЛЛАР, ВАКОЛАТЛАР ВА КАБИНЕТЛАР

| Роль | Асосий ваколат | Чегара |
|---|---|---|
| Owner / Superadmin | Барча бизнес созламалари, ходимлар, молиявий сиёсат, тасдиқлаш | Муҳим амаллар аудитдан ташқари қолмайди |
| Catalog manager | Рухсат берилган маҳсулот ва медиа | Молиявий ҳисоб-китоб ва бошқа ходим ҳуқуқларини ўзгартирмайди |
| Operator / Support | Бириктирилган буюртма, мижоз тасдиғи, алоқа ва қайтариш сўрови | Комиссияни яширин алмаштирмайди, тўловни ўзбошимча paid қилмайди |
| Warehouse / Delivery staff | Йиғиш, қадоқлаш, топшириш ва қайтган товарни қабул қилиш | Таннарх, тўлиқ ҳамкор молияси ва барча мижозлар экспорти йўқ |
| Finance | Тўловларни солиштириш, refund, payout тайёрлаш | Ўз ҳаракатини рухсатсиз иккинчи шахс сифатида тасдиқламайди |
| Partner | Ўз ҳаволалари, ўз буюртмалари, ўз комиссияси ва payout сўрови | Бошқа ҳамкор маълумоти, таннарх, нарх/қолдиқ таҳрири ва customer accountга кириш йўқ |
| Customer | Ўз буюртмалари, манзиллари ва мурожаатлари | Бошқа мижоз маълумоти йўқ |

Булар алоҳида компания ёки микросервис эмас. Бир код базасида permissions орқали бошқарилсин. Кичик жамоада бир одам бир нечта роль олиши мумкин; ҳар амалнинг ҳақиқий бажарувчиси сақлансин.

Frontendда тугмани яшириш етарли эмас. Backend endpoint, объект ва майдон даражасида ҳуқуқни текширсин. Айниқса order_id, partner_id, payout_id ва export учун owner/object scope мажбурий. Ҳамкор frontend юборган partner_idга қараб бошқа одам номидан ишлай олмасин.

## 05. АРХИТЕКТУРА ВА ИНФРАТУЗИЛМА

Ишлайдиган стек мавжуд бўлса, уни сақла. Бўш репозиторий учун тавсия: Next.js + TypeScript frontend; FastAPI, SQLAlchemy ва Alembic backend; PostgreSQL асосий база; зарур background ишлар учун битта worker ва Redis; маҳсулот медиа файллари учун алоҳида сақлаш.

Бу — таклиф, текширилмаган мавжуд код ҳақидаги даъво эмас. Амалда танланган версиялар ўзаро мос, қўллаб-қувватланадиган ва lockfile билан қотирилган бўлсин. Beta/RC версияни фақат рақами катталиги учун олма.

Модулли монолитдан бошла: identity, catalog, orders, attribution, inventory, payments, fulfillment, returns, commissions, support. Барча роллар битта ишончли backend бизнес мантиғидан фойдалансин. Frontendда комиссия ва қолдиқнинг мустақил ҳақиқат манбасини яратма.

Docker Compose лойиҳаси, database user, база, volume, network, портлар, environment ва секретлар Online Magazinга тегишли бўлсин. TAQVIM ресурсларини қайта ишлатма. Environment номи ўзгариши ўз-ўзидан бундай изоляцияни таъминлайди деб ҳисоблама; конфигурацияда исботла.

Kafka, Kubernetes, алоҳида payment/AI/affiliate микросервислари ва доимий вектор базасини биринчи кундан талаб қилма. Нарх ва қолдиқ учун PostgreSQL асосий манба. Redis йўқолса молиявий ҳақиқат йўқолмасин.

## 06. ДИЗАЙН, ТИЛ ВА ФОЙДАЛАНИШ ҚУЛАЙЛИГИ

Бу TAQVIM эмас: диний илова дизайнини кўчирма. Магазин учун ягона design tokenлар, типография, ранглар, тугма ва форма ҳолатларини ярат. Мавжуд бренд бўлса сақла; йўқ бўлса нейтрал ном ва алмаштириладиган логотип билан ишла.

Мижоз сайти mobile-first, оператор/админ қисми desktopда қулай ва телефонда ҳам ишлайдиган бўлсин. 320, 360, 390, 430, 768 ва 1280 pxда асосий оқимларни текшир. Катта шрифт, экран клавиатураси ва sticky тугмалар контентни беркитмасин.

Кирилл ва лотин матнлари translation keyлар орқали бошқарилсин. Номлар, SKU, URL, брендлар ва аралаш техник матнни кўр-кўрона транслитерация қилма. Тил алмашганда сават ва киритилган форма йўқолмасин. Рус тили кейинги кенгайтириш учун тайёр структурада қолиши мумкин, аммо чала таржимани тайёр тил сифатида чиқарма.

Loading, empty, validation error, retry, offline ва success ҳолатлари ҳар асосий экранда бўлсин. WCAG 2.2 AAга мослик мақсад қилиб олинсин: оддий матн контрасти 4.5:1, фокус ва клавиатура бошқаруви; лойиҳа талаби сифатида асосий touch майдонлари камида 44×44 CSS px. Бу 44 pxни WCAG AAнинг барча элементлар учун айнан минимал рақами деб таърифлама. [S5]

Сохта «ҳозир 124 киши кўрмоқда», тугамайдиган countdown, уйдирма шарҳлар ва захира камлигини қалбаки кўрсатиш тақиқланади.

## 07. РЎЙХАТДАН ЎТИШ ВА КИРИШ

Мижоз каталог ва саватдан рўйхатдан ўтмасдан фойдалана олсин. Буюртма тасдиғи телефонни текшириш ёки операторнинг мустақил тасдиғи билан бажарилсин. Тўлиқ аккаунт очиш хариднинг мажбурий шарти бўлмасин, аммо буюртма тарихига кириш тасдиқланган алоқа воситасини талаб қилсин.

OTP учун сўров частотаси, текшириш уринишлари, қайта юбориш оралиғи, амал қилиш вақти ва replay ҳимояси бўлсин. OTP логга ёки ҳамкор кабинетига чиқмасин. Бутун тизимда ишлайдиган «123456» bypass бўлмасин; demo provider фақат алоҳида test муҳитида.

Ҳамкор ариза беради, шартларни қабул қилади ва админ тасдиғидан кейин active бўлади. Pending, active, suspended, rejected ҳолатлари фарқлансин. Suspended ҳолат аввалги ҳақиқий даромадни ўчирмасин.

Ходимлар invitation орқали қўшилсин. Owner ва молиявий ваколатли ролларда иккинчи тасдиқ омили, сессияларни кўриш/бекор қилиш ва муҳим амал олдидан қайта аутентификация бўлсин.

Телефон, пароль ёки payout реквизити ўзгарганда тегишли огоҳлантириш ва сессия сиёсати ишласин. Мижоз телефон рақамини киритишнинг ўзи унинг аккаунтига кириш ёки аввалги буюртмаларини очиш ҳуқуқини бермасин.

## 08. МАҲСУЛОТЛАР, ВАРИАНТЛАР ВА МЕДИА

Маҳсулотда ном, slug, категория, қисқа/тўлиқ тавсиф, SKU, вариантлар, нарх, кўрсатиш ҳолати, етказиш учун зарур ўлчам/оғирлик, кафолат/қайтариш маълумоти ва медиа бўлсин. Ҳар сотиладиган вариант алоҳида SKU ва қолдиққа эга.

Таннарх, ички изоҳ ва комиссия қоидаси оммавий APIда чиқмасин. Ҳамкор фақат ўзига рухсат берилган комиссия маълумотини кўрсин. Draft, active, archived ҳолатлари; тарихда ишлатилган SKU физик ўчирилмасин.

Фото юклашда тур, ҳажм ва ўлчам текширилсин; thumbnail ва responsive форматлар тайёрлансин. Асл файл номи executable йўлга айланмасин. SVG/HTML каби фаол контент махсус тозалашсиз қабул қилинмасин. Alt text ва медиа тартиби таҳрирлансин.

CSV import аввал preview ва validation босқичидан ўтсин. Хатолар сатр бўйича берилсин. Қайта импорт SKUни дубликат қилмасин. Bulk editда қайси майдон ва нечта маҳсулот ўзгариши тасдиқдан олдин кўрсатилсин.

Маҳсулот ўчирилиши, номи ёки нархи ўзгариши аввалги order snapshotни бузмасин. Нарх тарихи ва комиссион қоида тарихи сақлансин.

## 09. МИЖОЗ САЙТИ, ҚИДИРУВ ВА САВАТ

Экранлар: бош саҳифа, каталог, категория, қидирув/фильтр, маҳсулот, сават, буюртма расмийлаштириш, натижа, буюртма ҳолати, шахсий кабинет, қайтариш/ёрдам, магазин ва ҳуқуқий маълумотлар.

Қидирув ном, SKU ва асосий хусусиятлар бўйича ишласин; кирилл/лотин, апостроф ва оддий ёзув фарқларини ҳисобга олсин. PostgreSQL имконияти етарли бўлса, алоҳида search кластер қўшма. Каталог бўш натижа, мавжуд эмас маҳсулот ва фильтрларни тозалаш ҳолатларига эга бўлсин.

Маҳсулот карточкасида ҳақиқий нарх, вариант, мавжудлик, етказиш ҳақи қандай ҳисобланиши ва қайтариш шартларига ўтиш кўринсин. Мобил харид тугмаси тушунарли бўлсин.

Сават guest сессияда сақлансин. Аккаунтга киришда миқдорлар назорат билан бирлаштирилсин. Сават сақланган нархни кафолатламайди: checkout сервердан янги ҳисоб олади. Нарх ёки қолдиқ ўзгарган бўлса, харидорга айтилсин.

Checkoutда исм, телефон, ҳудуд, манзил, етказиш усули, тўлов усули, товарлар ва якуний сумма кўринсин. Маркетингга розилик асосий буюртма шартларига қўшиб мажбуран белгиланмасин. Back/refresh тугмаси ёки double tap икки буюртма яратмасин.

## 10. НАРХ, ЧЕГИРМА ВА БУЮРТМА СУРАТИ

Пул binary floatда сақланмасин. UZS учун келишилган аниқликда integer minor unit ёки Decimal ишлат; API ва провайдер адаптерида бирлик очиқ белгилансин. Payme amount майдони тийинда бўлади. [S3]

Сервер ҳисоблайди: товарлар йиғиндиси − товар чегирмалари − тақсимланган буюртма чегирмаси + етказиш + қонуний ва олдиндан кўрсатилган қўшимчалар. Валюта, rounding ва солиқни кўрсатиш усули versioned pricing policyда бўлсин.

Биринчи релизда маҳсулот акцияси ва оддий promo code етарли. Чегирмалар биргаликда қўлланиш тартиби, лимит, амал қилиш муддати ва бекор қилиш қоидаси аниқ бўлсин. Промокод лимитини текшириш ва банд қилиш транзакцион бажарилсин.

Order line snapshot: product/SKU, ном/вариант, бирлик нархи, миқдор, line discount, order discount allocation, солиқ маълумоти, cost snapshot (фақат ички), commission policy version. Order snapshot: delivery quote, address, terms version, attribution, currency ва total.

Order-level чегирма сатрларга детерминистик тақсимлансин; қолдиқ rounding аниқ қоида билан тақсимланиб, сатрлар йиғиндиси якуний суммага тенг бўлсин. Refund оригинал тақсимотга асослансин, жорий нархга эмас.

Сервер quote version ва амал қилиш муддатини қайтарсин. Payment pending/confirmedдан кейин сумма яширин ўзгармасин. Ўзгартириш талаб қилинса, янги версия ва мижознинг қайта тасдиғи керак.

## 11. ҲАМКОР ҲАВОЛАЛАРИ ВА СОТУВ МАНБАСИ

Ҳамкор ҳар маҳсулот ёки тасдиқланган landing учун шахсий ҳавола олади. URL ичида телефон, банк реквизити ёки махфий токен бўлмасин. Очиқ referral code авторизация калити эмас.

Ҳамкор кампанияга ном ва UTM белгиларини қўша олади. Ҳақиқий partner ID серверда referral codeдан аниқланади. Нотўғри код, ўчирилган кампания ва suspended ҳамкор ҳолатлари аниқ бошқарилсин. Мижоз харид қилиши мумкин, лекин комиссия eligibility алоҳида баҳоланади.

Таклиф қилинаётган attribution сиёсати: мижоз checkoutда ихтиёрий киритган ва тасдиқланган ҳамкор коди устувор; акс ҳолда белгиланган ойнадаги охирги eligible referral босиши. 30 кун — фақат demo/test учун таклиф; live муддатни эгаси тасдиқлайди. Оддий direct кириш амалдаги eligible referralни автоматик ўчирмасин.

Browser чекловлари сабаб cross-device trackingни кафолатлама. Ихтиёрий код киритиш ёки тасдиқланган аккаунт боғланиши билан ишла. Яширин fingerprinting қўшма. Link preview ботлари сотув ёки ҳақиқий unique customer сифатида ҳисобланмасин.

Order яратилганда attribution snapshot қотирилади: partner, campaign, eligible touch, rule version, attributed_at ва reason. Кейинги cookie ёки бошқа ҳаволага босиш аввалги буюртманинг ҳамкорини ўзгартирмайди.

Битта буюртманинг eligible қисми учун битта ҳамкор; биринчи релизда multi-touch комиссия тақсимоти йўқ. Низо бўлса фақат ваколатли админ сабаб ва далил билан reversal/reallocation ёзади. Аввалги молиявий ёзув ўчирилмайди.

## 12. ҲАМКОР МИЖОЗ НОМИДАН БУЮРТМА КИРИТИШИ

Кабинетда «Мижоз учун буюртма» бўлсин. Ҳамкор маҳсулот/вариант/миқдорни танлайди, мижоз исми, телефони ва зарур етказиш маълумотини киритади. Манба ва мижоз билан келишув бўлгани қайд қилинади.

Бу амал customer accountга login қилиш эмас. created_by_user_id, customer_contact/profile_id ва attributed_partner_id алоҳида майдонлар. Ҳамкорнинг partner IDси backend аутентификациясидан олинади. У нарх, комиссия, paid статус ёки бошқа ҳамкор IDсини payload билан белгилай олмайди.

Яратилган буюртма аввал «Мижоз тасдиғини кутмоқда» ҳолатида. Мижоз ўз телефонига юборилган бир марталик код/ҳавола орқали тасдиқлайди ёки оператор мустақил равишда мижозга боғланиб тасдиқни қайд этади. Ҳамкор қўйган checkboxнинг ўзи мижоз шахси ёки розилигининг мустақил исботи деб қабул қилинмасин.

Мижозга товар, миқдор, нарх, етказиш ва магазин номи кўрсатилсин. Мижоз рад этса ёки алоқа ўрнатилмаса, автоматик жўнатиш ва комиссия йўқ. Ҳамкор ҳеч қачон мижознинг банк OTPсини ёки карта махфий маълумотини йиғмасин.

Бир телефонга ўхшаш SKU ва яқин вақтдаги буюртма текширув учун сигнал бўлсин, лекин ҳақиқий қайта харид автоматик блокланмасин. Ҳамкорга «бундай телефонли мижознинг фалон буюртмаси бор» деган шахсий маълумотни ошкор қилма. Дубликатни оператор ҳал қилади.

Аввал referral орқали шаклланган буюртмани бошқа ҳамкор қайта киритиб комиссияни ўғирлай олмасин. Тасдиқланган draft/lead давом эттирилса, унинг аввалги attributionи сақланади; зиддият алоҳида навбатга тушади. Customer confirmation ҳаволаси бир марталик, қисқа муддатли ва чекланган мақсадли бўлсин.

## 13. БУЮРТМА ҲОЛАТЛАРИ ВА ЎТИШ ҚОИДАЛАРИ

Ҳамма нарсани битта status майдонига жойлама. Қуйидаги мустақил ўлчамлар бўлсин:

| Ўлчам | Мисол ҳолатлар |
|---|---|
| Буюртма | draft, awaiting_confirmation, confirmed, cancelled, completed |
| Тўлов | unpaid, pending, paid, partially_refunded, refunded, failed, reconciliation_required |
| Етказиш | unallocated, reserved, picking, packed, shipped, delivered, failed, returned |
| Мижоз тасдиғи | pending, verified, rejected, expired |
| Қайтариш | requested, reviewing, approved, received, inspected, resolved, rejected |
| Комиссия | estimated, pending, available, reserved_for_payout, paid, reversed/adjusted |

Ўтишлар серверда guardлар билан бошқарилсин. Delivery=delivered бўлиши payment=paid дегани эмас. Refund товар автоматик омборга қайтди дегани эмас. Cancel молиявий reversal тугамасдан ҳамма жараён якунланди дегани эмас.

Ҳар ҳаракатда actor, reason, old/new state, timestamp, source ва request correlation сақлансин. No-op retry қайта хабар/комиссия яратмасин. Parallel edit учун revision/optimistic concurrency ишласин; эски revision билан таҳрир conflict берсин.

Қўлда бекор қилиш сабаблари, қайта очиш ва тўғрилаш ҳуқуқлари ҳужжатлансин. Мижозга тушунарли статусни backend фактлардан чиқар; ички техник ҳолатларни тўлиқ ошкор қилиш шарт эмас.

## 14. ОПЕРАТОР ХОНАСИ ВА CRM

Оператор учун амалий навбатлар: янги, мижоз тасдиғи кутилмоқда, қайта қўнғироқ, тўлов кутилмоқда, йиғишга тайёр, етказишда, муаммоли, қайтариш ва ёпилган. Ҳар навбатда масъул, кейинги амал ва кечикиш кўринсин.

Claim/assignment транзакцион бўлсин: икки оператор бир буюртмани бир вақтда ўзиники деб олмасин. Owner қайта бириктириши мумкин, сабаб аудитга тушади. Операторнинг бандлиги ва «қайта қўнғироқ қилиш вақти» бўлсин.

Буюртма карточкасида таркиб, ҳақиқий тўлов, манзил, тасдиқ, attribution, delivery ва изоҳлар timeline кўринсин. Телефон, товар ёки сумма ўзгарса, қайси босқичгача рухсат борлиги аниқ. Молиявий ҳолатни матнли изоҳ ёки «етказилди» тугмаси билан ўзгартирма.

Қўнғироқ натижаси structured: тасдиқлади, жавоб бермади, рад этди, маълумот нотўғри, кейин қўнғироқ. Оператор куни/навбат ҳисоботи бўлсин, аммо ходимнинг самарадорлигини фақат қўнғироқ сони билан нотўғри баҳолама.

Биринчи релизда телефония провайдери шарт эмас: телефонга ўтиш, натижа қайди ва task етарли. Қўнғироқ ёзиб олиш, автоматик оммавий қўнғироқ ва Instagram хабарларини норасмий йиғиш қўшилмасин.

## 15. ОМБОР, ҚОЛДИҚ ВА БАНД ҚИЛИШ

Битта омбор билан бошла, warehouse_idни кейинги кенгайтириш учун сақла. Ҳар SKUда on_hand, reserved ва sellable ҳолатларининг мантиғи аниқ бўлсин. Қолдиқ ҳаракатлари: қабул, банд қилиш, release, жўнатиш, қайтариш, текширувдан кейин қайта сотувга чиқариш, write-off ва inventory adjustment.

Sellable available = сотиш мумкин бўлган on_hand − active reservations. Манфий қолдиқ defaultда тақиқланади. Stock=1 бўлганда parallel иккита checkoutдан фақат биттаси охирги товарни банд қила олсин.

Қолдиқни UIда ўқиб кейин алоҳида decrement қилиш етарли эмас. PostgreSQL транзакцияси, conditional update ёки row lock, unique constraint ва retry сиёсати билан атомар бажар. Row locking ва deadlock бўйича танланган PostgreSQL версияси ҳужжатларига таян. [S6]

Тасдиқланмаган ҳамкор буюртмаси узоқ вақт омборни банд қилиб қўймасин. COD учун мустақил тасдиқдан кейин reservation; онлайн тўловда provider жараёнига мос reservation сиёсати. Cartнинг ўзи reservation эмас.

Reservation TTL жорий payment stateга боғлиқ. Provider транзакцияси очилганда унинг расмий муддат/бекор қилиш талабларини generic қисқа TTL билан бузма. Payme CreateTransaction ҳужжати буюртма/товарларни банд қилиш ва 12 соатлик transaction timeout қоидасини кўрсатади; productionда амалдаги протоколни текшир. [S3]

Муддати тугаган reservationдан кейин кечиккан payment тасдиғи келса, қолдиқни қайта текшир. Товар бўлмаса «тўланган, fulfillment муаммоси» навбати ва тасдиқланган refund/альтернатива оқими; манфий қолдиқ ёки сохта shipment йўқ.

## 16. ЕТКАЗИШ ВА COD

Биринчи релизда реал хизмат кўрсатиладиган ҳудудлар, манзиллар ва тарифлар админ томонидан бошқарилсин. Бутун Ўзбекистонга етказамиз деб автоматик ваъда берма. Ҳудуд таркибида мустақил шаҳарни мажбурий равишда нотўғри туманга киритма.

Тариф flat, ҳудуд бўйича ёки тасдиқланган содда қоида билан ҳисоблансин. Нарх ва тахминий вақт checkoutда кўрсатилсин; orderда snapshot сақлансин. «Бепул етказиш» қоидаси refund ва promo билан қандай ишлаши ҳужжатлансин.

Омбор picking list, қадоқлаш ва shipment ёзувини тайёрлайди. Delivery ходими/ташқи курьерга фақат унинг вазифаси учун керак маълумот берилади. Tracking ID, топшириш вақти, қабул қилиш далили, муваффақиятсиз уриниш ва сабаб қайд этилади.

Биринчи релизда буюртмани бир shipmentда жўнатиш default. Қисман етказиш фақат махсус функция ва item-level ҳисоб билан қўлланса ёқилсин; «ярми етди» деган изоҳ тўлиқ delivered статусига айланмасин. Қисман refund эса албатта қўллансин.

Нақд қабул қилиш (COD) учта фактга ажратилсин: мижоздан олинди, курьер/ходимда, магазинга топширилди ва молия солиштирди. Commission available учун қайси settlement талаби кераклиги версияланган сиёсатда белгилансин; default хавфсиз модель — маблағ магазинга тушиб тасдиқлангунча кутилмоқда.

## 17. ОНЛАЙН ТЎЛОВ, ФИСКАЛ ЧЕК ВА СОЛИШТИРИШ

Тўлов усуллари: тасдиқланган COD ва интеграция тайёрлигига қараб Payme/Click. Ҳар provider алоҳида adapter. Payme Merchant API ва Click Prepare/Complete бир хил callback схемаси деб тахмин қилинмасин. [S3, S4]

Биринчи жонли релиз учун камида битта онлайн providerнинг ҳақиқий интеграцияси тўлиқ текширилсин; иккинчиси тайёрликка қараб feature flagда. Калит йўқ бўлса test adapter ва contract testни бер, аммо live тўлов деб кўрсатма. COD-only pilot фақат эгаси алоҳида тасдиқлаганда ва чек/ҳисоб қоидалари ҳал қилинганда очилади.

Мижоз тўлови магазин merchant ҳисобига келади. Ҳамкор комиссиясини автоматик payment split билан боғлаш биринчи релизда шарт эмас; у алоҳида ҳисоб ва payout оқимидир.

Frontend return/success URL тўлов далили эмас. Paid ҳолати providerнинг аутентификацияланган server callbackи ёки ишончли reconciliation орқали белгиланади. Providerга мос имзо/auth, merchant/order ID, amount, currency ва transition текширилсин. Ҳар providerга бир хил HMAC схемасини уйдирма.

Webhook/inboxнинг provider transaction IDси unique бўлсин. Duplicate, out-of-order, cancel/perform рақобати, timeout ва server response йўқолиши тест қилинсин. Тўлов ёзуви, order projection ва outbox ўзгариши атомар. Ташқи HTTP чақирув пайтида узоқ DB lock ушлаб турма.

Бир буюртмага иккита ҳақиқий payment келса, иккинчисини «сўровни рад этдик» деб пулни ҳисобсиз қолдирма. Orphan/extra payment сифатида reconciliation навбати ва refund тартиби бўлсин.

Refund amount аввалги payment ва қайтарилган сумма билан чеклансин. Card PAN/CVV/банк OTPлари сайтда йиғилмасин; providerнинг стандарт тўлов саҳифаси афзал. Қисман refund providerда мавжудлиги алоҳида текширилсин, йўқ бўлса тасдиқланган manual жараён қайд этилсин.

Тўлов хабарномаси билан фискал чекни аралаштирма. Merchant ва товар турига мос фискаллаштириш, чекни тақдим этиш ва қайтариш чеки жараёни молия мутахассиси билан текширилсин. Provider statement ва ички payments ҳар куни/талаб бўйича солиштирилсин; фарқлар ёпилмагунча «ҳаммаси мос» дейилмасин.

## 18. БЕКОР ҚИЛИШ, ҚАЙТАРИШ ВА НИЗО

Customer/оператор RMA — қайтариш сўрови оча олади. Order line, миқдор, сабаб, зарур фото ва хоҳланган ечим қайд этилади. Харидорга очиқ шартлар ва версияси кўрсатилсин; эгаси белгилаган техник муддат қонуний ҳуқуқларни ўзбошимча чекламасин. [S1]

Тўловни қайтариш, товарни қабул қилиш, сотишга яроқлилигини текшириш ва комиссияни тузатиш алоҳида жараёнлар. Қайтган маҳсулот текширилмасдан sellable stockга қўшилмасин. Shipping fee, қисман чегирма ва хизмат харажатлари approved refund policyга асослансин.

Бир сатрдан 2 дона сотилиб, 1 дона қайтса, фақат шу миқдорнинг товар ва комиссия таъсири тузатилади. Goodwill price refund миқдорни камайтирмаслиги мумкин; бундай молиявий тузатиш алоҳида сабабга эга.

Refund request тасдиғи билан ҳақиқий банк refund тугагани фарқлансин. Натижа ноаниқ бўлса pending/reconciliation_requiredда қолсин. Retry иккинчи марта пул қайтармасин.

Ҳамкор комиссия бўйича низо оча олади. Ўз буюртмаси учун қайси қоида қўллангани, сумма ва тузатиш сабаби кўринсин. Бошқа ҳамкор ва мижознинг ортиқча шахсий маълумоти берилмасин. Низонинг масъули, далиллари ва қарор тарихи сақлансин.

## 19. КОМИССИЯ ҲИСОБЛАШ

Ҳар SKU/маҳсулот учун fixed-per-unit ёки percentage қоидасини қўлла. Иккаласи бир вақтда defaultда қўшилмасин. Rate, basis, currency, effective dates, refund behavior ва rule version сақлансин. Қоида йўқ маҳсулот учун комиссия кафолатлама; кабинетда аниқ кўрсат.

Буюртма пайтида қоида snapshot қилинади. Кейин эгаси ставкани ўзгартирса, аввалги буюртмалар ўз-ўзидан қайта ҳисобланмайди. Ҳамкорга кўрсатилган estimate сумма live price/refund ҳолати билан reconciliation қилинади.

Фоизли комиссия базаси — тасдиқланган қоидага кўра чегирмадан кейинги eligible товар қиймати. Етказиш ҳақи defaultда базага кирмайди. Солиқнинг базага кириши ёки чиқиши алоҳида аниқ policy; уни яширин тахмин қилма. Percentage basis point ёки аниқ Decimal билан сақлансин.

Комиссия дарҳол чиқаришга тайёр бўлмайди. Estimated → pending → available жараёнида мижоз тасдиғи, ҳақиқий payment, delivery, талаб қилинса COD remittance, қайтариш/низо ҳолати ва тасдиқланган hold муддати текширилсин. Ҳар айтилган факт backend далилига боғланган.

Hold муддати шартномавий ҳисоб-китоб қоидаси; кейин келган қонуний refundни рад қилишга асос эмас. Муддат эгаси тасдиқламаган бўлса автоматик release ёқилмасин.

Фоизли target = round(eligible retained goods base × rate). Fixed commissionда қайтган/бекор қилинган миқдор чиқарилади; retained товарга фақат нарх бўйича refund берилса тегишли комиссия қоида бўйича пропорционал тузатилади. Бир refundга quantity reversal ва value reversal икки марта қўлланмасин.

Ҳар воқеада олдинги target ва янги target фарқи журналга ёзилсин. Тўлиқ refund targetни нолга туширади. Duplicate delivery/payment/refund/worker retry бир хил unique business event орқали такрор ҳисобланмасин.

Тест мисоли (бизнес тарифи эмас): 100 000 сўмлик бирлик учун fixed 30 000 сўм. 2 дона тўланиб етказилса комиссия 60 000; 1 дона тўлиқ қайтса target 30 000. 30% қоидаси ва 10 000 сўм товар чегирмаси мисолида база 90 000, комиссия 27 000. Қолган 70 000 сўм автоматик соф фойда эмас.

## 20. МОЛИЯВИЙ ЖУРНАЛ ВА ҲАМКОРГА ПУЛ ТЎЛАШ

Ҳамкор кабинетида «кутилмоқда», «ечиш мумкин», «тўлов сўровида», «тўланган», «тузатилган» суммалар алоҳида. Бир умумий balance майдонини қўлда ошириш/камайтириш билан чекланма.

Commission/payout учун ўзгармас ledger ёзувлари, unique business reference ва source event бўлсин. Молиявий accountлар орасидаги ўтказмалар баланслаштирилган бўлсин; материаллаштирилган balance projection журналдан тикланади. Бу биринчи релизда тўлиқ бухгалтерия ERPси ёки мижозлар учун электрон ҳамён эмас.

Пул чиқариш сўрови фақат available маблағдан атомар reserve қилади. Parallel икки сўров бир маблағни икки марта банд қила олмасин. Pending комиссия чиқарилмайди. Минимал сумма, даврийлик, тўлов ҳақи ва ушлаб қолишлар тасдиқланган policy бўйича очиқ кўрсатилсин.

Ҳамкор payout реквизитларини текширади; кейинги ўзгартириш қайта тасдиқ талаб қилади. Сўров остидаги destination snapshot ўзгармасин. Молия тайёрлайди, ваколатли шахс тасдиқлайди. Кичик жамоада owner-only approval ишлатилса, бу алоҳида режим ва аудитда очиқ кўринсин; сохта икки шахсли тасдиқ яратма.

Биринчи релизда банк орқали қўлда ҳақиқий ўтказма ва тизимда reference/evidence билан тасдиқлаш мумкин. «Тўладим» тугмасининг ўзи пул кўчирмайди. Manual proof молия томонидан банк/реестр билан солиштирилади. Автоматик payout фақат provider расман қўллаганда ва алоҳида текширилганда.

Ташқи payout жавоби ноаниқ қолса, processing_unknown/reconciliation ҳолати; кўр-кўрона иккинчи ўтказма йўқ. Payout рад этилса reserve қайтарилади. Approved/processing пайтида refund келса ledger debt/hold қоидаси изчил бўлсин.

Комиссия тўланиб бўлгач товар қайтса, аввалги payout ўчирилмайди. Тузатиш ёзуви ва шартномада рухсат этилган кейинги даромаддан қоплаш/низо оқими ишлайди. Банк картасидан рухсатсиз пул ечиш йўқ. Ҳамкорга тузатиш сабаби кўрсатилсин.

## 21. ЭГА ПАНЕЛИ, ҲИСОБОТ ВА СОЗЛАМАЛАР

Owner панелида савдо, маҳсулот/қолдиқ, буюртма навбатлари, ҳамкорлар, операторлар, тўловлар, COD топшириш, refund, payout, ҳуқуқлар, контент ва интеграция ҳолати бўлсин. Feature flag ўчирилган модуль «ишлайди» деб кўрсатилмасин.

Кўрсаткичлар аниқ номлансин: яратилган буюртмалар, тасдиқланганлар, paid, delivered, COD pending, ҳақиқий тушум, қайтарилган пул, комиссия мажбурияти, payout ва ҳисобланган маржа. Яратилган order totalни ҳақиқий даромад деб чиқарма.

Тахминий операция маржаси: товар тушуми − таннарх − чегирма/қайтариш таъсири − комиссия − payment fee − магазин зиммасидаги доставка − киритилган реклама харажати − бошқа қайд этилган харажатлар. Таннарх ёки харажат етишмаса «соф фойда» ёрлиғи йўқ; ҳисоб тўлиқ эмаслиги билдирилсин.

Ҳисобот timezone, сана тури ва фильтрни очиқ кўрсатсин: order_created_at, paid_at ва delivered_at бир-бирига аралашмасин. Ҳамкор/кампания/товар бўйича аналитика, CSV экспорт, audit ва permission текшируви бўлсин. CSV formula injectionдан ҳимоя қил.

Эгаси ўз реклама кампаниялари UTM, бюджет ва сана оралиғини кирита олсин. Бошқарув панелидаги ҳисобланган attribution реклама платформасининг ҳисоботи билан айнан тенг бўлишини кафолатлама.

Эгаси target реклама учун маҳсулот landingини танлай олади. Shared product dataдан фойдаланиб, CTA, расм/видео, ҳақиқий афзалликлар, FAQ, етказиш ва қайтариш маълумотини чиқар. Landingдаги нарх каталогдан узилиб қолмасин.

Ҳамкорга тасдиқланган фото, тавсиф ва реклама матнлари кутубхонаси берилсин. У ўз ҳаволасини нусхалайди ва кампания статистикасини кўради. AI таклиф қилган матн эгаси тасдиғисиз расмий ваъдага айланмасин.

## 23. ХАБАРНОМАЛАР, TELEGRAM ВА SUPPORT

Хабар турлари: буюртма қабул қилинди, мижоз тасдиғи, payment натижаси, delivery ўзгариши, refund, комиссия available, payout натижаси ва support жавоби. Транзакцион хабар ва реклама обунаси ажратилсин.

## 24. AI — ЧЕКЛАНГАН, АМАЛИЙ ИНТЕГРАЦИЯ

AIни бутун савдони бошқарадиган автоном агент қилма. Биринчи релизда учта ёрдамчи етарли: каталог бўйича харид маслаҳатчиси; оператор учун жавоб/қисқа хулоса қораламаси; эгаси учун маҳсулот тавсифи қораламаси.

Мижоз ёрдамчиси фақат нашр қилинган каталог ва тасдиқланган FAQ/сиёсатлардан жавоб берсин. Нарх/қолдиқ live toolдан олинсин; жорий маълумотни ололмаса бор деб ваъда бермасин. Product ID, тушунтириш ва манба карточкалари қайтарилсин; output schema текширилсин.

Шахсий order status фақат серверда customer ownership текширилган tool билан очилади. Публичный чатда order рақамини билишнинг ўзи маълумот олишга етарли бўлмасин. Prompt injection permissionsни кенгайтирмасин. Каталогдаги матн instruction эмас, маълумот сифатида кўрилсин.

AI ўзбошимча order яратмайди, нарх/чегирма/қолдиқ ўзгартирмайди, payment/refund/payout бажармайди ва комиссия ҳисобламайди. Ҳамкорни автоматик жазолаш ёки даромадини ўчириш ҳуқуқи йўқ. Fraud signalни одам кўриб чиқади.

Provider abstraction, таймаут, rate limit, кунига бюджет, caching ва fallback бўлсин. Сайт, checkout ва оператор CRM AIсиз ҳам ишласин. AI ишламаса аниқ хабар ва оддий қидирув/операторга мурожаат қолади.

Ташқи AIга мижоз телефони, аниқ манзили, карта маълумоти ва тўлиқ ички база defaultда юборилмасин. Зарур бўлса минималлаштириш, қонуний асос ва data-flow approval. Оператор қораламаси инсон тасдиғисиз мижозга кетмасин.

AI ядро савдосидан кейин, алоҳида feature flag билан шу Phase 1нинг қўшимча қисми сифатида текширилади. Унинг калити йўқлиги асосий магазин кодини тугатишга тўсқинлик қилмасин.

## 25. МАЪЛУМОТЛАР МОДЕЛИ ВА API ШАРТНОМАЛАРИ

Асосий доменлар: users/roles/permissions/sessions; customer_profiles/contacts/addresses/consents; partners/agreements; products/variants/media/prices; campaigns/referral_touches/attribution_snapshots; carts/quotes/orders/order_items/history; inventory_movements/reservations; payment_attempts/provider_transactions/refunds/reconciliation; shipments/COD settlements; return_requests; commission_rules/entries/ledger; payout_requests; support; notifications/outbox; audit.

Бу жадвал номларини сўзма-сўз кўчириш эмас, масъулиятларнинг чеклистидир. Мавжуд базага мос нормаллаштирилган схема тайёрла. Payment, commission ва order тарихида foreign key, unique constraints ва индекслар бўлсин. Ўчирилган user/profile бўйича зарур молиявий тарихни қонуний retention сиёсати билан сақла/псевдонимлаштир.

OpenAPI шартномаларида request, response, validation, auth, role/object scope, idempotency ва error codeлар бўлсин. Endpoint йўналишлари: catalog/search, quotes/checkout, customer orders, partner links/orders/commissions/payouts, operator queue/claim/actions, admin catalog/rules, payment callbacks, finance reconciliation/refunds, shipment/returns, support ва ai/assist.

Order create, payment initiation, refund ва payoutда Idempotency-Key actor+endpoint+payload hash билан scopeлансин. Бир key ва бошқа payload conflict; бир key ва бир хил payload аввалги натижа. Key сақлаш муддати операция турига мос бўлсин; молиявий unique business reference ундан мустақил узоқроқ сақланади.

Async eventда event_id, aggregate_id, version, occurred_at бўлсин. Retry жараёнлари изчил, dead-letter/reconciliation queue бор. Export ва катта jobs pagination/checkpoint билан ишласин. Background worker ўчиб қайта ёқилганда бажарилган амал такрорланмасин.

## 26. ХАВФСИЗЛИК, МАХФИЙЛИК ВА ҚОНУНИЙ ИШГА ТУШИРИШ

Рухсатлар, объектга кириш, сессия, CSRF/XSS, upload, injection, rate limiting, секретлар ва logлар OWASP ASVS асосида тегишли текширувларга хариталансин. «ASVS сертификати» деган даъво қилинмасин; қайси талаб текширилгани кўрсатилсин. [S7]

Секретлар environment/secret storageда, .env.exampleда фақат placeholder. Production токен, OTP, пароль, карта маълумоти ва шахсий манзил оддий логларга чиқмасин. Public preview ва CIда фақат синтетик мижозлар. Secret scan ва dependency scan CIда бўлсин.

Оммавий оферта, сотувчи реквизитлари, етказиш, кафолат/қайтариш, privacy ва ҳамкор келишуви саҳифалари бўлсин. Уларнинг қабул қилинган версияси order/partner recordда қайд этилади. Энг муҳим ҳуқуқий қарорларни код ёзаётган AI мустақил «қонуний» деб тасдиқламасин. [S1]

Шахсий маълумотлар бўйича data-flow register: нима йиғилади, нима учун, ким кўради, қаерда сақланади, қанча сақланади, SMS/payment/delivery/AI провайдерига нима узатилади. Кириш, тузатиш ва ўчириш сўровлари ҳамда молиявий retention истиснолари ҳужжатлансин. [S2]

Жойлаштириш ва трансчегаравий узатиш талаблари амалдаги қонун матни билан текширилсин. 2026 йилда 27¹-модда таҳрири ўзгарган: эски «барча маълумот фақат Ўзбекистонда» деган умумий қоидани кўчирма; шунингдек «хоҳлаган давлатга ҳеч шартсиз» деган хулоса ҳам қилма. Маълумот тури, провайдер ва ҳимоя шартларини ҳуқуқий текшириш production gate ҳисобланади. [S2]

Онлайн тўлов merchant шартномаси, фискал чек, ҳамкорга тўлов/солиқ ҳисоботи, товар чекловлари ва қайтариш сиёсати тегишли мутахассис билан текширилмагунча оммавий савдога чиқарилмасин. Биринчи релиз оддий рухсат этилган истеъмол товарлари учун; лицензия/махсус чекловли товарлар учун алоҳида ишлаб чиқилмаган сценарийни очма.

## 27. КУЗАТУВ, ЗАХИРА, ТЕЗЛИК ВА АВАРИЯ ҲОЛАТЛАРИ

Ҳар request/order/payment/job учун correlation ID, structured log ва PII masking. Dashboard/alertлар: API хатолари, payment webhook failure, reconciliation фарқи, queue кечикиши, stock inconsistency, payout unknown ва backup failure. Ҳисоботда ҳақиқий ўлчанган ҳолат кўрсатилсин.

Бошланғич мақсадли load profile: 10 000 фаол SKU, 100 000 тарихий буюртма, 100 параллел браузер сессияси ва 10 параллел checkout. Бу production қуввати ҳақида кафолат эмас; benchmark шароити. Асосий сервер APIлари p95 ≤ 500 ms мақсад, ташқи provider latency алоҳида; 1%дан кам хатолик ва нол oversell/duplicate payout. Кўрсаткичлар реал тест муҳитида ўлчансин.

Фойдаланувчи checkoutда узоқ кутса request ID билан ҳолатни текшириш мумкин бўлсин; қайта босиш дубликат order яратмасин. Payment/stock операцияларида хавфли қўлда қайта уриниш ўрнига reconciliation йўли.

Мобил асосий саҳифалар учун optimized media, caching, pagination ва кичик JavaScript budget. Карточка юкланмагунча layout сакрашини камайтир. Бизнес ядронинг тўғрилигини тезлик учун бузма.

Backup алоҳида ресурсда шифрланган ва access чекланган. Restore репетициясида PostgreSQL, медиа, migration version ва зарур конфигурация тикланиши текширилсин. Муҳитлар аралашмасин. Бошланғич таклифий мақсад: RPO ≤ 1 соат, RTO ≤ 4 соат; буни фақат керакли backup/PITR ва restore синови билан тасдиқла. Инфра етмаса бажарилди деб ёзма, реал натижа ва фарқни кўрсат.

Migration олдин backup, compatibility ва rollback/roll-forward режаси. Backupни тиклаш янги ҳақиқий тўловларни йўқотиб қўйиши мумкин: тўғридан-тўғри «эски базани қўя қолиш» эмас, payment reconciliation ва молиявий recovery тартиби бўлсин.

| Payme/Click | Adapter, fixtures, мавжуд sandbox | Merchant шартнома, калит ва ҳақиқий test натижаси |
| SMS/Telegram | Fake SMS ёки test bot | Расмий provider ва алоҳида Online Magazin бот |
| Фискаллаштириш ва солиқ | Схема, маълум blocked ҳолат | Мутахассис текширган тартиб ва интеграция |
| Қайтариш/кафолат/оферта | Draft ва version tracking | Амалдаги қонунга мос текширилган матн |
| Hosting/data processors | Фақат синтетик маълумот | Data-flow ва ҳуқуқий текширув |
| AI provider/модель/лимит | Mock ва evaluation fixture | Калит, бюджет, data policy ва functional eval |

Ҳар қарорда owner, status, approved_at, effective_at, version ва source_note бўлсин. Қоида ўзгарса тарихга retroactive таъсир фақат алоҳида migration/adjustment режаси ва тасдиқ билан.

# ИЛОВА C. ҲИСОБ-КИТОБ ВА ИДЕМПОТЕНТЛИК ЭТАЛОНЛАРИ

Мақсад — кичик бизнесни тўлиқ банк тизимига айлантириш эмас, пулни нотўғри санашни олдини олиш.

1) Payment amount ҳақиқий provider транзакциясига боғланган; order рақами бир ўзи етарли unique external payment ID эмас.
2) Customer payment, COD remittance, commission liability ва partner payout бир хил воқеа эмас.
3) Ҳар молиявий ўзгаришда source_type + source_id + effect_version unique. Retryни фақат frontend кнопкасини ўчириш билан ҳал қилма.
4) Availableдан reserved_for_payoutга ўтиш бир транзакцияда; external transfer узоқ DB transaction ташқарисида, аммо уникал payout attempt билан.
5) Refundдан кейин commission target қайта ҳисобланади; аввалги targetга фарқи adjustment, original ledger entry таҳрирланмайди.
6) Refund orderда умумий сумма бўлиб эмас, affected line, quantity ва financial allocation билан қайд этилади. Шундан stock ва commission ўз таъсирини олади.
7) Қўлда коррекция actor, сабаб, далил ва тасдиқ билан; «балансни тўғрилаб қўйиш» учун яширин SQL update йўқ.
8) Ҳисобланган маржа билан statutory net profit бир хил эмас; бухгалтерия экспорти ва солиқ ҳисоботи алоҳида масъулият.
9) Журналдан balance ва projectionsни қайта қуриш тест қилинади; асосий immutable recordсиз фақат cached numberга ишонма.
10) Пул қайтариш ёки payout натижаси ноаниқ бўлганда хавфсиз ҳолат — reconciliation; автоматик success ёки кўр-кўрона retry эмас.
